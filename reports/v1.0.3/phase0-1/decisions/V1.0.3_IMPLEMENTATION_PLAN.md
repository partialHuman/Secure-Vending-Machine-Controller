## 2. Parameter Architecture

### 2.1 Where the Value Lives
`rtl/top.sv` owns the single authoritative parameter value. The package owns only the **default** and the **maximum limit**:

```
transaction_pkg   PRODUCT_ID_WIDTH      = 5 (unchanged)
                  PRODUCT_COUNT_MAX     = 2**PRODUCT_ID_WIDTH      // 32 (derived)
                  PRODUCT_COUNT_DEFAULT = 5
top  #(parameter int PRODUCT_COUNT = transaction_pkg::PRODUCT_COUNT_DEFAULT)
 ├─ validation: D-102 Mechanism 2 (top.sv only)
 ├─ security_engine   #(.PRODUCT_COUNT(PRODUCT_COUNT))
 ├─ inventory_manager #(.PRODUCT_COUNT(PRODUCT_COUNT))
 └─ transaction_controller, payment_interface, payment_arbiter, balance_manager,
    timeout_controller, response_generator, crc8 → unchanged (do not consume count)
```

No new external ports are added to `rtl/top.sv`. Existing testbench instantiations `top dut(...)` remain valid via the package default.

### 2.2 Type and Range Strategy

| Parameter Feature | Choice | Reason |
|---|---|---|
| **Parameter Type** | `parameter int` (signed) | Permits detection of negative or zero values; matches package convention |
| **Valid Range** | **1 … `PRODUCT_COUNT_MAX` (32) inclusive** | 5-bit ID space accommodates 0–31; count 32 makes every ID valid |
| **Product ID Port** | `[transaction_pkg::PRODUCT_ID_WIDTH-1:0]` | Eliminates hard-coded `[4:0]` literals |
| **Structural Clamp** | `localparam int unsigned PC_SAFE = (PRODUCT_COUNT < 1) ? 1 : (PRODUCT_COUNT > transaction_pkg::PRODUCT_COUNT_MAX) ? transaction_pkg::PRODUCT_COUNT_MAX : PRODUCT_COUNT;` | Submodules keep arrays structurally legal during elaboration so the D-102 top-level check produces the clean intended diagnostic |
| **Submodule Validation** | **No competing validation block** | Single authoritative validation in `top.sv`; submodules use `PC_SAFE` |

### 2.3 D-102 Resolution — Rejection of Invalid Parameter Values

Empirical results from Vivado 2018.2 Probes A, B, and the N=33 extra test determined the mechanism:
* **Mechanism 1 (Generate `$error`):** Rejected. Downgraded to a warning by `xelab`, exit code `0`.
* **Mechanism 2 (Undefined Module Fallback):** **Approved and Adopted.** Valid configurations (`N=5`, `N=32`) elaborate cleanly (exit `0`). Invalid configurations (`N=0`, `N=33`) halt static elaboration with exit code `1` and diagnostic `ERROR: [VRFC 10-2063] Module <PRODUCT_COUNT_OUT_OF_RANGE_see_docs> not found`.
* **Mechanism 3 (Runtime `$fatal`):** Retained as optional simulation-time defense-in-depth, but not relied upon for primary elaboration gating.

#### Illustrative Implementation Construct (For Phase 2)
In `rtl/top.sv`:
```systemverilog
// Authoritative parameter range validation (Vivado 2018.2 compatible)
generate
    if (PRODUCT_COUNT < 1 || PRODUCT_COUNT > transaction_pkg::PRODUCT_COUNT_MAX) begin : g_bad_count
        PRODUCT_COUNT_OUT_OF_RANGE_see_docs u_invalid ();
    end
endgenerate
```

> [!IMPORTANT]
> The code snippet above is an approved architectural design specification. In compliance with Phase 0/1 restrictions, **no project RTL has been modified in this task**.

#### Scope Note on Synthesis
The Mechanism 2 behavior has been verified for simulation static elaboration (`xelab`). Behavior under Vivado Synthesis (`synth_design`) is currently **unverified by experimental evidence** and will not be claimed as verified without explicit synthesis testing.

## 3. Inventory Manager — Structure and Guard Semantics (D-103, D-107, D-108)

Table depth in `rtl/inventory_manager.sv` is set to `PC_SAFE` (5 at default).

### 3.1 Deterministic Behavior for IDs ≥ `PC_SAFE`
* **Reads (`read_en=1`):** Return `price=0`, `quantity=0`, `stock_available=0`, `stock_ok=0`, `low_stock=0`.
* **Reads (`read_en=0`):** Return all zeros (unchanged).
* **Writes / Decrements:** Ignored (`update_price`, `update_qty`, `purchase_en` do not alter memory).
* **Reset:** Initializes valid indices `0 .. PC_SAFE-1` to price `(i+1)*10` and quantity `20`.

Table accesses sit inside `if (id_valid)` blocks (where `wire id_valid = (product_id < PC_SAFE);`).

### 3.2 Evidence Boundaries and Phase 2 Verification Requirements (D-103 & D-108)
* **D-103 Verification Boundary:** Probe E verified the relevant SystemVerilog language features (package constant functions, `$size`, `$bits`, safe out-of-range reads returning unknown, hierarchical localparam access). Actual `inventory_manager` array depth and top-level parameter propagation have **not** been verified in RTL during Phase 0/1; these constitute explicit Phase 2 verification requirements.
* **D-108 Verification Boundary:** Probes D and E demonstrated isolated guarded-index and out-of-range read behavior in standalone probe testbenches. Actual `inventory_manager` invalid-access handling has **not** yet been tested in RTL; Phase 2 requires direct unit tests in `tb_inventory_manager.sv` verifying that out-of-range reads return safe zeros, out-of-range writes/decrements are ignored, and a per-entry memory snapshot of valid entries `0 .. PC_SAFE-1` confirms zero memory corruption before and after invalid operations.
