# Verification

Directed, self-checking simulation in Vivado XSIM. **This is not formal verification** and it has not been shown to catch every defect.

## 1. How to run

Linux / macOS (Bash):
```bash
SVM_REQUIRE_MANIFEST=1 vivado -mode batch -source scripts/run_regression.tcl
```

Windows (PowerShell):
```powershell
$env:SVM_REQUIRE_MANIFEST="1"; vivado -mode batch -source scripts/run_regression.tcl
```

Outputs in `build/` (git-ignored): `logs/`, `reports/<testbench>/`, `PROVENANCE.txt`, `regression-summary.txt`. A testbench passes only if it prints `SVM_TB_RESULT: PASS total=N ...`, the simulator process exits with return code 0, and `N` equals the value recorded in `scripts/expected_checks.txt`. Options: `SVM_TBS`, `SVM_STRICT_KL`, `SVM_REQUIRE_MANIFEST`, `SVM_UPDATE_MANIFEST` (see `scripts/README.md`).

Total checks across all four testbenches: **497 checks**.

Check counts per testbench are specified by the release manifest `scripts/expected_checks.txt`. The v1.0.1 release reported 69 / 101 / 101 / 56 (327 total); v1.0.2 added tests and monitors, increasing the verified check count to 497.

## 3. What a "check" is

One call to `check_result`, `check_internal` or `check_condition`, or one conservation check. A check count is **not** a count of distinct behaviors: the coin and card testbenches repeat the same scenarios, and loops count each iteration.

## 4. Independent monitor (v1.0.2)

Every testbench contains an always block that counts, independently of the test sequence:

- accepted requests (`request_valid && request_ready`),
- rising edges of `response_valid`,
- clocks where `response_valid` stays high (wider than one cycle),
- requests deliberately aborted by a test reset.

At the end of each run a check requires `accepted == responses + aborted`. A wide response pulse is reported as `SVM_KNOWN_LIMITATION: KL-002` rather than failing (it is a known defect); `SVM_STRICT_KL=1` makes it fail.

## 5. Expected values: where they come from

Expected values are **hand-written per test** (literals such as "exact payment gives refund 0"). There is no independent reference model yet (planned: VER-002), so a test and the design can share a wrong assumption. Two are known and labelled: overpayment `refund == 0` (KL-001) and the timeout test's `refund == 0` (KL-002). New v1.0.2 boundary tests deliberately do **not** assert the refund of an overpayment.

## 6. White-box techniques

`force`/`release` is used for: transaction-ID forcing (duplicate), `packet.crc` corruption (CRC), FSM state hold (timeout). These conditions cannot be produced through the ports (KL-006, KL-007, KL-002). The coin testbench's CRC force uses a self-referential expression and the force/release timing relative to the clock is race-sensitive; these tests pass in the maintainer's runs but are tool- and ordering-sensitive. Planned replacement: unit testbenches (VER-004).

## 7. Latency definition (changed in v1.0.2)

Reported latency is clocks from the accepting edge until `response_valid` is first sampled. In v1.0.1 the count started before the request was driven, so every value was one clock larger. Derived expectations (confirmed by regression): success and out-of-stock 11, insufficient balance 10, security rejection 8, forced-timeout test about 26. Reports generated by v1.0.1 and earlier are not comparable.

## 8. Known gaps (see `known-limitations.md`)

- No random or coverage-driven tests; no bound assertions; no formal proofs.
- No test of overpayment *change* (the behavior does not exist; change is forfeited per KL-001).
- `payment_type` 6/7, `ERR_CRC` and `ERR_DUPLICATE` through the public port are not testable.
- Vivado 2018.2 is the only tool tested; other tool versions are untested.
- Gate G8 (synthesis / timing closure / linting) is formally not applicable to v1.0.2 and is deferred to v1.2.0 (Milestone M-E).
